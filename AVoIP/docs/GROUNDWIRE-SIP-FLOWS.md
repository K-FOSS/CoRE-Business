# Groundwire SIP and media flows

This page documents the source-backed behavior of the Groundwire native SIP
client in the YVR/Home1 AVoIP deployment. It describes extension `7101` in
realm `sipcore.mylogin.space` and uses the supplied Groundwire diagnostic
details as observational evidence. A client diagnostic is not proof that
every backend hop or media packet completed; those claims are marked
accordingly.

The implementation uses [Kamailio 6.1](https://www.kamailio.org/),
[FreeSWITCH](https://developer.signalwire.com/freeswitch/), and
[Sipwise RTPEngine](https://github.com/sipwise/rtpengine). Kamailio's
[registrar](https://www.kamailio.org/docs/modules/6.1.x/modules/registrar.html),
[usrloc](https://www.kamailio.org/docs/modules/6.1.x/modules/usrloc.html),
[auth_db](https://www.kamailio.org/docs/modules/6.1.x/modules/auth_db.html),
and [TOPOS](https://www.kamailio.org/docs/modules/6.1.x/modules/topos.html)
modules provide the SIP state and topology boundary.

## B. Signaling architecture

### Native TLS registration and client-originated calls

```text
Groundwire
  │ TLS 8443, SNI sipcore.mylogin.space
  ▼
main-gw / Envoy TLSRoute (TLS passthrough)
  │ advertised frontend TLS listener 5064; PROXY v2 peer metadata
  ▼
internal-websocket Kamailio StatefulSet, 3 replicas
  │ private TLS 5062 to call control
  ▼
FreeSWITCH core-managed profile, TLS 5072
  │ Admin-managed dialplan and call policy
  ├── registered AoRs through Kamailio PostgreSQL registrar
  └── carrier/internal routes through the configured AVoIP path
```

The chart's native SIP frontend uses the Gateway API TLS route and a
dedicated public Kamailio listener. TLS is not terminated by Envoy for the SIP
message stream; the client certificate check is performed by the frontend
Kamailio certificate. The current deployment evidence shows Kamailio receiving
the frontend traffic on `5064/tls` and FreeSWITCH receiving the private call
control leg on `5072/tls`. The exact public load-balancer address is supplied
by the active Gateway and DNS configuration, not hardcoded in this chart.

### Inbound call to 7101

```text
PSTN/provider or internal caller
  → carrier/internal Kamailio policy
  → FreeSWITCH managed DID/extension routing
  → TLS 5062 to the owning internal-websocket Kamailio
  → PostgreSQL location lookup for 7101
  → owner Path/connection for each TLS or WSS contact
  → Groundwire on its established TLS flow
```

For a direct registered AoR call, the internal-websocket route normalizes the
Request-URI to the registrar realm, checks the active subscriber, performs
`lookup("location")`, records the dialog route, and relays the INVITE. The
registered contact's Path and owner metadata are binding-specific. A shared
location row does not make a live TCP/TLS connection portable between pods.
The registrar enables `append_branches=1`, so the lookup keeps the highest-q
binding as the Request-URI and adds every other active binding as a transaction
branch. TM then rings all registered TLS/WSS endpoints in parallel; each branch
retains its own Path, TOPOS owner, and flow alias.

### Groundwire to extension 66

The client sends an initial INVITE over the public TLS flow. Kamailio performs
the device-side `proxy_authorize()` check against the `active_subscriber`
view, challenges if needed, verifies that the authenticated username is
`7101`, removes the device Authorization headers, and adds the trusted
`X-Core-Extension` identity before sending the INVITE to FreeSWITCH. FreeSWITCH
matches `core-managed-entry`, then its Admin-managed dialplan chooses the
internal destination. The route is not a hardcoded “Groundwire-to-66” bypass.

The observed example with `CSeq: 2126` and `422 Session Interval Too Small`
was generated by FreeSWITCH and forwarded by Kamailio. The current correction
sets `enable-timer=true` and `minimum-session-expires=120` on `core-managed`.
Kamailio raises a sub-120-second initial offer (including the browser's
60-second offer) to the deployed FreeSWITCH floor before the hop, retaining
any refresher parameter. It does not synthesize a retry or create a second
INVITE transaction.

### Groundwire to PSTN

```text
Groundwire → public TLS frontend Kamailio
  → authenticated X-Core-Extension identity
  → FreeSWITCH core-managed / Admin policy
  → internal Kamailio private TLS carrier route
  → selected provider/trunk
```

AVoIP Admin supplies the routing snapshot, extension permissions, caller-ID
and provider policy. Kamailio validates the trusted extension metadata and
provider/site policy; Helm values provide the deployment boundary and
allowlisted integration, not per-call authorization. Provider failover and
carrier selection must be verified from the active Admin snapshot and live
logs for a particular call.

## C. Registration, authentication, and HA ownership

Kamailio loads `auth_db`, `registrar`, and `usrloc` for the enabled
`internal-websocket` private-SBC instance. PostgreSQL TLS uses hostname
verification. `usrloc` runs in database mode 3, so the `location` and
`location_attrs` rows are shared by the three replicas. The migration creates
the standard Kamailio tables plus the AVoIP `active_subscriber` view and a
trigger that purges contacts when a verifier is disabled, expires, deleted, or
has its HA1 changed.

The registration sequence is:

1. The frontend accepts REGISTER on the public TLS or WSS listener.
2. It adds a transport alias from the actual accepted flow. For TLS behind
   Envoy, the code uses the accepted connection peer tuple rather than the
   phone's Contact port; for WSS, the owner flow is retained separately.
3. `PRIVATE_REGISTER` checks the realm, exact allowed AoR, source peer class,
   and username-to-AoR match.
4. `www_authorize()` validates the realm-specific HA1 in
   `active_subscriber`.
5. The route removes a device-supplied Path and writes the owner Path for the
   registering StatefulSet replica, then `save("location")` writes the
   binding.
6. Kamailio returns the registrar response. The response's Contact list is
   binding state; it is not permission to connect to a Kubernetes hostname
   from the client.

The chart defaults are two contacts, 120-second minimum expiry, and
600-second maximum expiry; the YVR injected instance raises the allowed
contact count to eight for 7101. The effective values should be confirmed from
the rendered YVR application before relying on them operationally.

Three replicas can therefore see the same registration rows, but only the
replica that accepted a TLS/WSS connection owns that live transport. TOPOS
stores dialog topology in the configured site-local Redis/Valkey database,
while the accepted socket remains process-local. A different replica can
forward an in-dialog request to the owner through the owner TLS listener, but
it cannot recreate a dead connection to the client's ephemeral source port.

Registration survives a pod restart in PostgreSQL until expiry/revocation;
the underlying TLS/WSS flow does not. A client must reconnect and REGISTER.
During a rolling update, an active dialog is expected to fail if its owning
socket is terminated; this is not transparent active-call failover.

## D. Inbound ringing and teardown

The destination lookup and ringing policy are split between AVoIP Admin and
the SIP routing layer. FreeSWITCH handles managed call control and invokes the
configured registered-client target; Kamailio resolves the active contacts
and preserves each contact's owner route. TLS and WSS contacts may coexist in
the same AOR up to `maxContacts`.

For parallel ringing, the expected transaction behavior is provisional
responses from branches, one winning 2xx, and CANCEL to losing branches. The
implementation must be validated with two simultaneously registered contacts;
the source shows the registration and routing machinery, but this document
does not claim a fresh two-device race was captured.

ACK, BYE, CANCEL, UPDATE, INFO, PRACK, REFER, NOTIFY, and MESSAGE are admitted
on the SIP Core route. TOPOS and Record-Route restoration select the owner
route; the frontend's public Route is not blindly used as the next hop for a
client-facing dialog. RTP teardown is attempted on BYE and dialog-end paths.
If the owner pod or its accepted connection disappears, the supported result
is an explicit flow failure or transaction timeout, followed by client
re-registration—not a connection to the old ephemeral port.

## E. Media, ICE, RTP, and SRTP

```text
Groundwire ICE/SDP
  ⇄ Kamailio rtpengine_manage()
  ⇄ RTPEngine control (private UDP 22222 or configured control transport)
  ⇄ RTPEngine public media interface, UDP media range
  ⇄ FreeSWITCH RTP/SDP leg
```

The frontend sends native phone offers through RTPEngine with
`replace-origin`, `external internal`, and `address-family=IP4`. Native TLS
clients receive the `SDES-nonew` compatibility flag when the configured
policy permits SDES; browser WSS receives the WebRTC flag. This distinction is
intentional: browser WebRTC flags must not be applied indiscriminately to
native SIP phones.

The first offer creates the media session. Final answers are processed once
per outgoing wire copy using the existing media session; retransmitted 200
responses must retain the same rewritten address, ports, ICE credentials,
candidates, and security negotiation. A BYE/dialog-end path deletes the
RTPEngine session. The chart uses the site-injected RTPEngine public address
and UDP media range; the supplied evidence observed public media address
`24.86.197.63` and ports in `11000–11279`, but those values must be read from
the active site configuration rather than copied into a deployment manifest.

STUN server-reflexive candidates are connectivity checks, not TURN relay
allocation. A client having a STUN URL in its configuration does not prove
that TURN was used. The source handles RTPEngine ICE/SDP rewriting and
trickle-ICE INFO updates; it does not establish that every iPad IPv6 or tunnel
candidate is reachable. The active RTP candidate pair, RTCP path, and whether
the client used a host, server-reflexive, or relay candidate require a packet
capture or RTPEngine log correlated by Call-ID/session handle.

## G. Presence, SUBSCRIBE, NOTIFY, SIPIS, and voicemail

The SIP Core request allowlist includes SUBSCRIBE only where the rendered
route's method set permits it; the current private route explicitly handles
NOTIFY but the chart does not define a general presence publisher. The source
does not show a complete Groundwire presence/BLF or message-summary service.
Successful client SUBSCRIBE/NOTIFY behavior and voicemail MWI therefore remain
unverified. `*97` is a dialplan/voicemail operation, not evidence that MWI
subscriptions are implemented.

The supplied diagnostic references `s-8.sipis.acrobits.cz`, but no SIPIS-
specific route, credential broker, push webhook, or server-side registration
logic appears in this repository. The implementation source therefore
supports only this conclusion: SIPIS behavior is client/provider-side and is
not proven to be an active AVoIP registrar or duplicate contact here. Direct
foreground SIP/TLS registration is distinct from Apple push wake-up. Locked or
suspended iPad delivery requires a Groundwire/SIPIS/APNs test; it cannot be
inferred from Kamailio's PostgreSQL contact row.

## H. Findings and verification plan

### Confirmed by source or supplied evidence

- `7101` is an explicitly allowed registrar user in the YVR injected values.
- Digest authentication uses a realm-specific HA1 and the active subscriber
  view; device Authorization is removed before the trusted FreeSWITCH hop.
- Registration data is shared in site-local PostgreSQL mode 3, while live
  TLS/WSS connection ownership remains replica-local.
- TOPOS uses Redis/Valkey-backed topology state; it does not transfer a live
  socket between pods.
- Native and WSS media branches are distinguished. Native phone SDP uses the
  SDES-compatible path; WSS uses WebRTC flags.
- A captured `422` was generated by FreeSWITCH with `Min-SE: 120`; the
  correction is a consistent 120-second `core-managed` UAS floor plus
  Kamailio normalization of shorter client offers. This lets a WebSocket
  client offering 60 seconds proceed without a client-side retry.

### Not established from the supplied data

- The exact active ICE candidate pair, RTCP behavior, or TURN allocation.
- A two-contact parallel-ring race and losing-branch CANCEL.
- A complete 7101 inbound call through a carrier DID after the latest rollout.
- A call kept alive beyond 40 seconds with ACK, BYE, and RTPEngine cleanup.
- Locked-device SIPIS/APNs wake-up and absence of duplicate contacts.
- Presence, MWI, SUBSCRIBE authentication, and NOTIFY semantics.
- Transparent active-call survival across a Kamailio pod restart; the design
  explicitly does not promise it.

### Recommended live checks

1. Register Groundwire and a second 7101 contact; verify both PostgreSQL
   `location` rows, owner Paths, expiry refresh, and deregistration without
   exposing credentials.
2. Place an internal 7101→66 call and an inbound call to 7101. Correlate the
   client Call-ID across frontend Kamailio, FreeSWITCH, owner forwarding,
   RTPEngine, and final BYE/200 responses.
3. Keep one call established for more than 40 seconds, send UPDATE/INFO, and
   hang up from each side. Confirm one RTPEngine delete and no reconnect to an
   ephemeral Contact port.
4. Repeat with the call entering a non-owner frontend replica and with the
   owner pod restarted. Confirm the expected flow failure/re-registration
   behavior rather than claiming failover.
5. Inspect final client-facing post-TOPOS Contact and SDP, not only pre-TOPOS
   diagnostics. Verify the public hostname, stable route set, identical
   retransmitted SDP, and a reachable media candidate.

Rollback for the session-timer correction is a Git revert of the
`enable-timer`/`minimum-session-expires` profile change followed by the normal
scoped Argo reconciliation. Do not roll back by changing registrar rows or
exposing client credentials.
